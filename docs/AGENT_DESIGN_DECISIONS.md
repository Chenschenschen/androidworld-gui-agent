## Observation and grounding are independent

| Combination | Advantage | Cost/risk |
| --- | --- | --- |
| Screenshot + coordinates | Sees custom drawing, icons, and layout; close to the model's advertised visual GUI use | Image processing and visual localization; coordinate scaling must be correct |
| Tree + indices | Exact exposed text/bounds; code resolves index to a location; avoids image processing in the request | Missing/unlabelled controls; repeated labels; an old index can point at a different element |
| Screenshot + tree + indices | Visual context and code-based pointing together | Both input costs; more context; model must understand the numbered mapping |
| Tree/indices with image fallback | Avoids images on screens where the tree suffices | Requires a fallback trigger; a nonempty tree can still omit the relevant control |

An index is a position in **one observation's element list**, not a permanent
element ID. The model still has to choose the correct semantic target. Code
lookup reduces one source of pointing error; it does not guarantee success.

Day 1 p.41 recommends index grounding when the tree is useful. The official
[GELab-Zero model card](https://huggingface.co/stepfun-ai/GELab-Zero-4B-preview)
describes interaction from visual cues. This supports testing a visual baseline;
it does **not** prove that this installed model supports our proposed index
schema or that tree-only input will work equally well. Check its official prompt,
actual response, and local Ollama rendering before selecting an interface.

Day 1 p.40 gives illustrative image/tree token estimates. They are not measured
costs for our model. Locally, compare wall time, prompt-processing time where
available, generation time, input sizes, RAM/VRAM, and target correctness.
JPEG/PNG byte compression alone does not establish lower visual token cost.

## Alternatives, reasons, and revision conditions

### D01–D05: observing and pointing

**D01 — Observation**

- Alternatives: pixels only; tree only; both each step; tree with image fallback.
- Agreed comparison: compare pixels/coordinates and tree/indices on identical saved
  screens first. Reason: lower input cost is useful only if the model can use
  that interface correctly. Keep all raw observations in logs whichever we send.
- Risk: a saved-screen probe tests interface use, not end-to-end task success.
- Revisit: measured latency/resource pressure, absent target in the tree, or
  consistent differences in target correctness. Hybrid is a later candidate.

**D02 — Grounding**

- Alternatives: native coordinates; indices resolved by code; explicit fallback.
- Proposal: make this conditional on D01 and the actual model interface. Test
  indices if the model can select them; use checked coordinate conversion for
  visual actions. Never silently snap a predicted point to the nearest element.
- Risk: indices can be ambiguous or stale; coordinates can land on empty space.
- Revisit: `grounding` failures with evidence of the correct intended target.

**D03 — Image preparation**

- Alternatives: original resolution; aspect-preserving downscale; crops; labelled
  overlays. Model preprocessing can change cost independently of file size.
- Proposal: establish a readable visual reference, then compare one downscaled
  version if necessary. Keep the original screenshot and record the exact
  image dimensions and transform sent to the model.
- Risk: shrinking loses small text; crops lose context; overlays obscure content.
- Revisit: resource pressure or missed small controls. Convert points from the
  model's documented coordinate domain into device coordinates explicitly.

**D04 — Tree input**

- Alternatives: full tree; visible actionable elements; compact labels with
  states/bounds; numbered overlays alongside an image.
- Proposal: a compact list with text/content description, type, relevant state,
  bounds, and an explicit observation-local index map. Include informative text
  as well as buttons, so important values do not disappear during filtering.
- Risk: token reduction can remove relevant text; repeated labels need context.
- Revisit: a missing target/value or confusing repeated labels. Inspect omissions
  before adding more prompting.

**D05 — Freshness**

- Alternatives: assume stability; wait then read a new screen; recheck a target
  when the screen changes before execution.
- Proposal: one observation ID per step, one dependent GUI action at a time;
  discard a stale choice and request a new decision if its mapping changed.
- Risk: asynchronous UI changes can invalidate both indices and coordinates.
- Revisit: a selected element moves, a dialog opens, or execution reports a
  mismatch. Do not reuse an old index against a newly numbered list.

### D06–D10: local inference

**D06 — Model/engine**

- Alternatives taught: laptop; controlled server; cloud API; different engines.
- Chosen: local GELab-Zero through Ollama, per the user. Reason: course model,
  existing installation, and understandable local deployment.
- Risk: local memory and latency constraints. A different model/provider changes
  the experiment; the course allows alternatives, but our user preference is local.
- Revisit: only through an explicit recorded user decision. No fallback model.

**D07 — Precision**

- Alternatives: current BF16; a separately named 8-bit model; 4-bit model.
- Proposal: retain current precision for compatibility measurements. Consider a
  separate quantized variant only if memory/latency becomes a measured blocker.
- Risk: quantization can change formatting and task reliability. It is not a
  free speed improvement and must not overwrite the reference model silently.
- Revisit: measured memory/latency problem; reevaluate quality after a change.

**D08 — Hardware and residency**

- Alternatives: current CPU setting; supported GPU offload; unload between calls;
  keep the model loaded during a run.
- Proposal: inspect hardware support and actual residency first; measure cold
  load separately from warm calls. The reported `num_gpu=0` is a setting, not a
  measurement of actual utilization. Do not promise GPU availability.
- Risk: emulator and model compete for memory; repeated loading distorts timing.
- Revisit: observed load cost, memory pressure, or supported acceleration.

**D09 — Sampling/reproducibility**

- Alternatives: installed settings (`temperature=1`, `top_k=20`, `top_p=0.95`);
  low-temperature baseline; controlled temperature comparison; fixed/varying seeds.
- Proposal: verify the model's recommended settings, then choose one recorded
  baseline. A low-temperature variant is a candidate for a controlled comparison,
  not an assumed improvement. Keep task seed separate from generation seed.
- Risk: low temperature can repeat a wrong choice; fixed seeds do not guarantee
  identical GUI timing or bit-for-bit results across systems.
- Revisit: parse drift, repeated mistakes, or poor success across repeated runs.

**D10 — Context/output/resource budgets**

- Alternatives: current `num_ctx=4096`; a larger measured context; shorter input;
  short/long output allowance and request timeouts.
- Proposal: measure a real formatted request, reserve output space, and set
  bounded budgets from local timings. The theoretical architecture limit is not
  the active context window. Numeric settings are still undecided.
- Risk: short budgets truncate actions; larger contexts consume more memory;
  hidden truncation loses facts. Input metrics can have cache-dependent semantics.
- Revisit: truncation, timeout, out-of-memory, or context overflow evidence.

### D11–D15: history and memory

**D11 — History policy**

- Alternatives: all images/actions; latest observation plus recent actions;
  latest observation plus recent actions and an exact scratch note.
- Chosen in principle: latest observation + recent actions + exact task values when needed.
  Reason: avoid resending every old image while preserving values for multi-app
  tasks. The number of recent steps is not chosen yet.
- Risk: short history hides earlier failures; full history can overflow locally.
- Revisit: `lost_value`, repetition, or growing context/latency.

**D12 — Overflow/compression**

- Alternatives: stop with an explicit context-budget error; truncate oldest
  turns; summarize them; selectively reload an earlier observation.
- Proposal: keep original logs on disk, protect goal/exact values, and compress
  descriptive history only when measured growth requires it. Prefer a simple
  deterministic representation before adding a separate summarizer call.
- Risk: summaries lose details; truncation forgets; retrieval can return the wrong
  step. A sliding window also changes the reusable prefix.
- Revisit: long tasks approach the budget or compression removes needed evidence.

**D13 — Within-run scratch memory**

- Alternatives: rely on history; free-text summary; structured exact fields with
  source observation/step; retain/reload the source observation itself.
- Chosen in principle: use exact scratch notes when needed. Proposed implementation:
  a small per-run record for required strings/numbers and provenance.
  Copy task-given values exactly. UI-derived values must come from observed
  content and retain their source; Python must not supply an unseen answer.
- Risk: extraction can be wrong; lossy paraphrases break note merging; automatic
  clipping can remove required content.
- Revisit: `lost_value` or incorrect order. Clear this memory on every new run.

**D14 — Cross-session memory**

- Alternatives: none; stable user preferences only; reusable procedures;
  accumulated task episodes/answers.
- Proposal: no automatic benchmark memory across runs. Keep project preferences
  in our development documents; do not inject earlier benchmark answers.
- Risk: leakage makes repeated runs incomparable; stale preferences mislead.
- Revisit: an explicit need for personalized service or a separate labelled
  learned-procedure experiment. Within-run scratch memory is a different choice.

**D15 — Persistent memory lifecycle, if added**

- Alternatives: notes, narratives, simple JSON fields, advanced linked records;
  code extraction or model extraction; overwrite, append, merge, or expire.
- Proposal: defer. If needed, use small structured records with source, scope,
  timestamp/version, and explicit correction/deletion. Separate episodic,
  semantic, and procedural entries only where it helps the task.
- Risk: model extraction invents facts; generalization discards exceptions;
  clustering/pruning adds maintenance. The D2 lab saves a hard-coded dictionary,
  not automatically parsed model extraction.
- Revisit: real persistent facts that cannot fit in a simple file.

### D16–D22: status, planning, and prompts

**D16 — Status contents/ownership**

- Alternatives: model recounts history; code maintains all status; code counters
  plus separately labelled model-estimated progress.
- Proposal: Python tracks attempted model calls, executed actions, errors,
  remaining budgets, and current observation ID. Count errors too. A proposed
  TODO completion is not an official verifier result.
- Risk: a status record is a lossy projection and cannot replace original logs.
- Revisit: a useful missing status field. Do not add fields without a purpose.

**D17 — Status update strategy**

- Alternatives: append each small snapshot; replace the latest snapshot; update
  less frequently; compact old snapshots at a declared boundary.
- Confirmed: replace status in each request; retain every snapshot on disk.
  Reason: limits growth and confusion from historical status. Accepted downside:
  changed status can require cache recomputation. The learning agent implements
  current step, step budget, prior call count, and observation ID.
- Risk: appending bloats context; replacement costs recomputation; stale snapshots
  may be mistaken for current state. Full on-disk logs stay append-only either way.
- Revisit: actual context growth, stale-status errors, or measured processing cost.

**D18 — Planning**

- Alternatives: select one next action; generate a full initial plan; maintain
  a short revisable TODO list; separate planner model/call.
- Confirmed: one generic agent selecting one action from current evidence. Add
  a short TODO list for longer tasks only if it helps preserve order/subgoals.
- Risk: no plan can lose progress; a fixed long plan goes stale after UI changes;
  extra planner calls add latency and complexity.
- Revisit: wrong order, missed subgoals, or repeated navigation in real traces.

**D19 — Prompt process/format/examples**

- Alternatives: many independent rules; short ordered process; Markdown/XML
  sections; no examples versus a few boundary examples.
- Proposal: preserve the model's expected interface, with a concise process:
  inspect → choose allowed action → execute → inspect feedback. Add examples
  only for demonstrated ambiguity, keeping them fixed within an experiment.
- Risk: many rules/examples consume context; changing a trained format can
  reduce compatibility. XML labels help organize data, but are not a safety wall.
- Revisit: specific instruction/format errors. Do not hard-code a benchmark tap
  sequence or correct task answer into a supposedly generic example.

**D20 — API/roles/template**

- Alternatives: standard chat messages; model-specific documented rendering;
  native tool calls; structured/textual action response parsed by Python.
- Proposal: inspect GELab-Zero's actual reference interface and Ollama payload
  before picking the API. Preserve role boundaries when supported; do not invent
  `USER:`/`ASSISTANT:` concatenation as a shortcut.
- Risk: `{{ .Prompt }}` and capability metadata do not prove correct role/image
  rendering. The course's native tool demo is not proof this GUI model uses it.
- Revisit: real image/template/tool-call incompatibility. Record the chosen API.

**D21 — Prefix/cache design**

- Alternatives: changing system prompt/tool order; fixed prefix with dynamic
  suffix; optimize only after measurements.
- Proposal: keep core instructions, examples, and action definitions/order
  stable; append task-specific state late. Measure warm paired requests as in
  D2 rather than claiming a cache hit from identical text alone.
- Risk: dropping/replacing old observations changes the prefix too. Cache reuse
  across requests is engine-dependent and is different from a memory store.
- Revisit: prompt-processing time dominates or the chosen history policy prevents
  useful reuse. No custom cache infrastructure in the first agent.

**D22 — Skills**

- Alternatives: none; a task/app-triggered procedure; user-triggered loading;
  model-selected skill catalogue; all procedures always in the system prompt.
- Proposal: defer until an observed failure benefits from a reusable procedure.
  If added, choose explicit triggers and append the procedure once at invocation.
- Learning variant implemented: conditional inline `CONTACTS_GUIDE` after
  surname loss; general instructions explicitly read from `instructions/agent.md`.
  A combined context repair passed once; guide-only benefit is still unmeasured.
- Risk: wrong trigger, stale instructions, prefix bloat, or a task-specific solution
  disguising a fixed script as an agent. Skills give knowledge; tools give actions.
- Revisit: recurring app procedure errors; reevaluate and label the skill variant.

### D23–D29: actions, feedback, and stopping

**D23 — Action space/app switching**

- Alternatives: small standard GUI allowlist; full Android World action space;
  exact app opening; launcher navigation.
- Proposal: expose only GUI actions needed for the agreed tasks, including
  typing, navigation, wait, completion, and pointing compatible with D02.
  Prefer supported exact `open_app` mapping over ambiguous launcher search.
- Risk: too few actions make a task impossible; too many increase confusion.
  Arbitrary shell/SQL/filesystem actions are not model tools for task completion.
- Revisit: a valid required action is missing or `wrong_app` appears.

**D24 — Definitions and action scheduling**

- Alternatives: all definitions upfront; compact catalogue with on-demand
  definitions; fixed small action schema. Independent tools may run in parallel;
  dependent GUI actions cannot safely do so without new observations.
- Proposal: a fixed compact action contract for one GUI action per step. Reason:
  few tools do not justify a discovery framework or parallel UI mutation.
- Risk: verbose definitions cost tokens; progressive loading adds routing errors.
- Revisit: action space grows substantially beyond this project.

**D25 — Output/parser/validation**

- Alternatives: model-native action format; requested JSON; supported constrained
  decoding; permissive parsing; strict parsing with a bounded correction attempt.
- Proposal: match the verified model interface, then normalize to Android World
  actions. Check action name, required fields, types, bounds, index mapping,
  text/app arguments, and mutually exclusive targets before executing.
- Risk: forcing a new schema may hurt compatibility; forgiving parsing can
  change the intended action. Never run model text with `eval` or a shell.
- Revisit: measured parsing errors. Preserve raw responses, including truncation.

**D26 — Errors/retries**

- Alternatives: stop on first error; bounded correction/retry; unlimited retry;
  retry all errors identically.
- Confirmed in part: one correction request after invalid output, then stop;
  no invalid action executes. Classify API, parse, execution, and verification
  errors separately. Learning execution errors stop; an uncertain action is
  not replayed automatically. Its recovery policy remains open.
- Risk: an action may have executed before a timeout; replay can duplicate data.
- Revisit: recurring recoverable errors. Counters include attempts, not just
  successful responses. Infrastructure failures are not invented PASS/FAIL.

**D27 — Readiness/no progress**

- Alternatives: fixed sleeps; Android World's stable-state observation;
  explicit wait/check; repeated-action detector.
- Proposal: inspect a fresh stabilized observation after each action. Detect
  repeated equivalent actions with no meaningful state change; provide feedback,
  then stop within a bound rather than retry indefinitely.
- Risk: screenshots can change because of a clock/spinner; identical screenshots
  do not prove failure of a clipboard operation. No single image hash is enough.
- Revisit: `too_early`, stalled screens, or repetition; choose numeric bounds from
  traces instead of assigning arbitrary budgets now.

**D28 — Completion/verifier timing**

- Alternatives: model `done` alone; observation check then final official verifier;
  official verifier after every step; selected intermediate verifier checks.
- Required: official verifier determines task success, separately from agent done.
- Proposal: an observation check before completion and official verification at
  termination/budget stop. Decide intermediate checks only after inspecting each
  task verifier; do not expose privileged verifier data as normal GUI observation.
- Risk: model stops early; per-step verification can add cost or have side effects.
- Revisit: `false_done` or verifier contract issues. Log evaluation errors honestly.

**D29 — Screen content as data**

- Alternatives: merge all text into instructions; label sources/roles and enforce
  a runtime action allowlist; confirm every action versus declared task scope.
- Proposal: distinguish trusted goal/rules from app text and model output. Python
  enforces the action boundary on the test emulator. Authorized benchmark SMS
  stays inside the emulator; no confirmation for every reversible test tap.
- Risk: a note/web page may contain instructions that conflict with the real goal.
  Prompt labels alone are not a permission boundary. A venv is dependency isolation.
- Revisit: expansion beyond the emulator or real-world consequences, where the
  authorization scope would need a new explicit decision.

### D30–D35: evidence and optional retrieval

**D30 — Logs/metrics**

- Alternatives: final summary only; full raw trajectory; compact model context
  with full original evidence on disk.
- Required: trajectory and evaluation video. Proposal: unique per-run folders;
  immediate request/action/result records; raw replies and metadata; observation
  files; settings snapshot; stop reason; official verifier outcome separately.
- Risk: logs alone do not prove task success; token/cache fields have different
  semantics across engines. Do not invent hidden reasoning or missing metrics.
- Revisit: missing evidence during a failure analysis. Screen probes get setup/
  probe labels and are not counted among the required evaluation runs.

**D31 — Comparisons and change control**

- Alternatives: change multiple settings together; one-variable comparisons;
  fastest-run/demo-only reporting; repeated comparable instances.
- Required: three evaluation runs per task. Proposal: frozen task/configuration
  snapshots, paired instances/seeds for comparisons, and one recorded change at
  a time. Report counts, success rates, latency, errors, and interventions.
- Risk: cold load/order/UI randomness confound timing; three runs are a small
  sample. An observation+grounding comparison changes an interface package,
  so it cannot isolate the causal effect of either part by itself.
- Revisit: ambiguous results. Add a controlled follow-up instead of claiming causality.

**D32 — Tasks/reset**

- Alternatives: start with hard tasks; incremental learning tasks; final easy /
  medium / hard selection; fixed or varied generated parameters.
- Chosen: Wi-Fi, note, note+SMS first; calendar and either merge notes or OsmAnd
  later. Reason: learn the same loop before longer memory/navigation demands.
- Required: at least one task per course difficulty category. Proposal: official
  setup/reset and fresh per-run memory; record instances and device-time setup.
- Revisit: final hard-task choice when the loop is understood; compare variants
  on equivalent instances and keep the harder presentation objective visible.

**D33 — Failure/improvement**

- Alternatives: enlarge the model; add every mechanism upfront; select one small
  change supported by a trace.
- Required: at least one failure analysis and documented improvement comparison.
- Proposal: use `grounding`, `too_early`, `lost_value`, `wrong_app`, `false_done`
  as primary GUI failure classes, with infrastructure errors separate. Record a
  root-cause hypothesis and pick one targeted change from the evidence.
- Risk: the visible symptom can differ from the cause; the improvement can fail.
- Revisit: before/after evidence contradicts the hypothesis. Preserve failures.

**D34 — Need for RAG**

- Alternatives: none; directly supply a small reference; exact step/file lookup;
  keyword retrieval; embedding/vector retrieval.
- Proposal: defer RAG. Screens, task instructions, and a small scratch record
  do not automatically need a document retrieval pipeline.
- Risk: retrieval can supply irrelevant/stale evidence and add complexity.
- Revisit: a concrete large external knowledge source is needed. UI element
  indexing in D02 is unrelated to the document index used by RAG.

**D35 — Retrieval design/evaluation, if added**

- Alternatives: keyword versus embeddings; fixed-size versus structure-aware
  versus semantic chunks; chunk size/overlap; top-k; source/time filters;
  reranking; evidence inserted at different positions in context.
- Proposal: defer. Start with the smallest sufficient lookup. If document RAG is
  necessary, compare retrieval independently before task-answer quality, using
  Recall@k, MRR, or nDCG where appropriate. Keep sources and version information.
- Risk: wrong chunk boundaries, poor ranks, stale evidence, extra dependencies.
- Revisit: measured retrieval misses. Retrieval metrics cannot replace Android
  World task success metrics.

## Agreed first-round rationale and planned comparison

**D01/D02 — Compare before choosing.** Reason: visual coverage and exact tree
pointing address different failure modes, and our installed model's compatibility
must be measured. Accepted downside: a small extra probe stage. Reconsider if one
interface cannot work with the actual model contract; document that limitation
instead of treating unsupported input as a normal task failure.

**D11/D13 — Latest observation, recent actions, exact scratch notes when needed.**
Reason: limit old-image/context growth while retaining values needed across apps.
Accepted downside: we must identify which facts to retain and might omit earlier
context. Reconsider after `lost_value`, repeated actions, or missing evidence.
History length, scratch fields, and extraction rules remain open; original logs
stay intact on disk. The choice does not enable cross-run memory.

**Runtime priority — Balance verified success and manageable runtime.** Reason:
the presentation needs both demonstrable correctness and a usable local run.
Accepted downside: neither the smallest request nor the slowest maximum-quality
configuration automatically wins. No latency ceiling has been chosen yet.
Reconsider if actual call/run times make repeated evaluations impractical.

The interface comparison will start with one paired compatibility probe and
expand only if the model can consume both interfaces:

- Save a screenshot and its tree from the same observation. Use the same task
  instruction and intended visible target for both methods.
- Method A receives the screenshot and chooses coordinates. Method B receives
  the numbered tree and chooses an index. Validate the actual supported output
  contract for each; preserve any added instructions as part of that variant.
- Evaluate whether the chosen index identifies the intended target or the point
  falls inside its independently inspected bounds. A syntactically valid reply
  is not sufficient. Missing tree targets count as coverage limitations.
- Hold model identity, precision, hardware, sampling, history, and task goal
  constant where possible. Record any unavoidable interface differences.
- Separate cold load/warm-up from measured calls, repeat compatible probes,
  alternate method order, and retain all replies/errors. Agree the expanded
  screen set and numeric budgets after the first compatibility result.
- Compare target correctness, formatting errors, elapsed/processing/generation
  time where available, input size/context metrics with their actual meaning,
  and resource use. No claimed cache hit from shared text alone.
- These are offline interface probes: they do not tap the device or establish
  official task success. Later task runs must test closed-loop behavior and
  use the official verifier and video.

This compares two **observation/grounding packages**. It cannot, by itself,
prove which component caused a difference. A hybrid or single-variable follow-up
is justified only if the initial evidence makes it useful.
